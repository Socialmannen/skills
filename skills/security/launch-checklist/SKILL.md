# Launch Readiness Checklist for AI-Built Apps

Use this skill to audit, review, and harden web applications before public launch or major releases.

## Audit Workflow

When invoked:
1. **Scope the app:** Identify backend (Supabase/Firebase/custom), auth method, external SDKs, payments (Stripe), AI features, and user content capabilities.
2. **Step-by-step verification:** Run through the 11 stages below. For each item:
   - Mark as **[PASS]**, **[FAIL]**, or **[N/A]** with the exact file and code reference.
   - For any **[FAIL]**, provide the concrete remediation code or configuration.
3. **Generate Action Items:** Prioritize fixes by `[Must do]` vs `[Should do]` before taking real users or payments.

# The launch checklist for AI-built apps

From https://ducktate.com/learn/launch-readiness/ (checked 2026-10-09). Not legal advice.

## Stage 1: Lock down your data

- [ ] Turn on Row Level Security for every table in every exposed schema, then write a policy for each action the app needs. [Must do] Sources: Supabase RLS guide (https://supabase.com/docs/guides/database/postgres/row-level-security), Postgres row security (https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- [ ] Test as a stranger: with only the public key and no login, try to read and write every table. [Must do] Sources: Palmer on CVE-2025-48757 (https://mattpalmer.io/posts/2025/05/statement-on-CVE-2025-48757/), Wiz on Moltbook (https://wiz.io/blog/exposed-moltbook-database-reveals-millions-of-api-keys)
- [ ] Test as the wrong user: sign in as one user and request another user's records by changing IDs. [Must do] Sources: OWASP A01:2025 (https://owasp.org/Top10/2025/A01_2025-Broken_Access_Control/), Wiz on Base44 (https://www.wiz.io/blog/critical-vulnerability-base44)
- [ ] Read every policy your agent wrote, and replace any rule that only checks for a login with one that checks ownership. [Must do] Sources: Firebase insecure rules (https://firebase.google.com/docs/rules/insecure-rules), OWASP Authorization Cheat Sheet (https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)
- [ ] On Supabase, revoke the default anon and authenticated grants on tables that should not be public, and grant only what the app needs, before the 2026-10-30 change. [If it applies] Sources: Supabase changelog (https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically), Supabase RLS guide (https://supabase.com/docs/guides/database/postgres/row-level-security)
- [ ] On Firebase, replace Test mode rules before launch. [If it applies] Sources: Firebase insecure rules (https://firebase.google.com/docs/rules/insecure-rules)
- [ ] Keep the secret or service_role key on the server; only the publishable or anon key may appear in browser or app code. [Must do] Sources: Supabase API keys (https://supabase.com/docs/guides/api/api-keys)
- [ ] Check that no NEXT_PUBLIC_ or VITE_ variable holds a secret, then search the built output for secret key prefixes. [Must do] Sources: Next.js environment variables (https://nextjs.org/docs/app/guides/environment-variables), Vite env variables (https://vite.dev/guide/env-and-mode)
- [ ] Turn on GitHub secret scanning and push protection; if a secret reaches git, rotate it first, then clean up. [Should do] Sources: GitHub push protection (https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection), OWASP Secrets Management (https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)
- [ ] Write a one-page breach plan: who decides, how you reach users, and which deadlines apply where your users are. [Must do] Sources: GDPR Art. 33 (https://gdpr-info.eu/art-33-gdpr/), California SB 446 digest (https://calmatters.digitaldemocracy.org/bills/ca_202520260sb446), Washington RCW 19.255.010 (https://app.leg.wa.gov/RCW/default.aspx?cite=19.255.010), 50-state survey (https://privacyrights.org/resources-tools/reports/data-breach-notification-laws-50-state-survey-2026-edition)
- [ ] Rate limit login, password reset and one-time code endpoints, and send basic security headers. [Should do] Sources: OWASP Authentication Cheat Sheet (https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), OWASP Secure Headers (https://owasp.org/www-project-secure-headers/), Supabase rate limits (https://supabase.com/docs/guides/auth/rate-limits)
- [ ] Do not treat your platform's built-in security scan as your security review. [Should do] Sources: Lovable security docs (https://docs.lovable.dev/features/security)

## Stage 2: Third parties and dependencies

- [ ] Make a list of every third-party script, font, SDK and vendor your app loads, on every page and screen, with the personal data each one receives. [Must do] Sources: GDPR Art. 28 (https://gdpr-info.eu/art-28-gdpr/), OWASP Top 10:2025 (https://owasp.org/Top10/2025/)
- [ ] Remove each script or SDK on that list that you cannot give a clear reason for. [Should do] Sources: Munich Regional Court, 3 O 17493/20 (https://www.gesetze-bayern.de/Content/Document/Y-300-Z-GRURRS-B-2022-N-612)
- [ ] Self-host your web fonts instead of loading them from Google's servers, especially if you have visitors in the EU. [Should do] Sources: Munich Regional Court, 3 O 17493/20 (https://www.gesetze-bayern.de/Content/Document/Y-300-Z-GRURRS-B-2022-N-612)
- [ ] Sign or accept the data processing agreement of every vendor that handles your users' personal data, if the GDPR applies to you. [If it applies] Sources: GDPR Art. 28 (https://gdpr-info.eu/art-28-gdpr/)
- [ ] Publish a list of your subprocessors and say how people can learn about changes to it. [Should do] Sources: GDPR Art. 28 (https://gdpr-info.eu/art-28-gdpr/)
- [ ] Check the license of every dependency, keep the MIT and similar notices, and keep GPL and AGPL code out of a closed product unless you have decided to comply. [Must do] Sources: MIT license (https://opensource.org/license/mit), GPL FAQ (https://www.gnu.org/licenses/gpl-faq.html#GPLRequireSourcePostedPublic), AGPL v3 (https://www.gnu.org/licenses/agpl-3.0.txt)
- [ ] Commit your lockfile and install pinned versions, not whatever is newest. [Should do] Sources: CISA alert on npm (https://www.cisa.gov/news-events/alerts/2025/09/23/widespread-supply-chain-compromise-impacting-npm-ecosystem)
- [ ] Run npm audit or OSV-Scanner on every build and make a high-severity finding stop the build. [Should do] Sources: npm audit (https://docs.npmjs.com/cli/v11/commands/npm-audit), OSV-Scanner (https://google.github.io/osv-scanner/)
- [ ] Turn on Dependabot alerts for your repository. [Should do] Sources: GitHub Dependabot alerts (https://docs.github.com/en/code-security/dependabot/dependabot-alerts/about-dependabot-alerts)
- [ ] Before you accept a change from your agent, check that every new package it added exists and is the real one you meant. [Must do] Sources: arXiv 2406.10279 (https://arxiv.org/abs/2406.10279)
- [ ] When a supply-chain attack hits a package you use, rotate your GitHub, npm and cloud credentials. [If it applies] Sources: CISA alert on npm (https://www.cisa.gov/news-events/alerts/2025/09/23/widespread-supply-chain-compromise-impacting-npm-ecosystem), GitHub npm security plan (https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/)
- [ ] Update the vendor list and your public subprocessor list every time you or your agent add a script, SDK or service. [Should do] Sources: GDPR Art. 28 (https://gdpr-info.eu/art-28-gdpr/)

## Stage 3: The paperwork

- [ ] Write a data inventory from your real code: every field, SDK, analytics tool, AI provider and log, where each one sends data, and for how long you keep it. [Must do] Sources: Apple App Review Guidelines 5.1.1 (https://developer.apple.com/app-store/review/guidelines/), GDPR Art. 13 (https://gdpr-info.eu/art-13-gdpr/)
- [ ] Start from a template, then edit it to match what your app really does. [Should do] Sources: General Legal templates (CC0) (https://github.com/General-Legal/legal-templates), Basecamp policies (https://github.com/basecamp/policies)
- [ ] Make sure your privacy policy covers the six CalOPPA items: PII and third-party categories, how a user can review and request changes to their own PII if you offer that, how you announce changes, the effective date, your Do Not Track answer, and whether third parties may track users over time and across sites. [Must do] Sources: Cal. Bus. & Prof. Code Sec. 22575 (https://california.public.law/codes/business_and_professions_code_section_22575)
- [ ] If people in the EU can use your app, add the GDPR Article 13 items: who you are, purposes and legal basis, recipients, transfers, retention, rights, and the right to complain. [If it applies] Sources: GDPR Art. 13 (https://gdpr-info.eu/art-13-gdpr/), GDPR Art. 3 (https://gdpr-info.eu/art-3-gdpr/)
- [ ] Read the finished policy against your inventory and delete or fix every promise the app does not keep. [Must do] Sources: FTC on OkCupid (https://www.ftc.gov/news-events/news/press-releases/2026/03/ftc-takes-action-against-match-okcupid-deceiving-users-sharing-personal-data-third-party), Cal. Bus. & Prof. Code Sec. 22576 (https://california.public.law/codes/ca_bus_and_prof_code_section_22576)
- [ ] Post the privacy policy as a public web page, not a PDF, and link it from your app and your store listing. [Must do] Sources: Cal. Bus. & Prof. Code Sec. 22575 (https://california.public.law/codes/business_and_professions_code_section_22575), Google Play User Data policy (https://support.google.com/googleplay/android-developer/answer/10144311)
- [ ] If you use Google sign-in or list on Google Play, host the policy on your own domain and link it from the OAuth consent screen. [If it applies] Sources: Google OAuth verification (https://support.google.com/cloud/answer/13464321), Google Play User Data policy (https://support.google.com/googleplay/android-developer/answer/10144311)
- [ ] Show your terms at sign-up with an unticked "I agree" box or a button that says it means agreement, with the terms linked next to it, and save who agreed to which version. [Should do] Sources: Nguyen v. Barnes and Noble (https://cdn.ca9.uscourts.gov/datastore/opinions/2014/08/18/12-56628.pdf), Berman v. Freedom Financial (https://www.courtlistener.com/opinion/6458861/daniel-berman-v-freedom-financial-network-llc/)
- [ ] Put a cookie notice on your site that lists each cookie or similar storage and why, and get consent first for anything not strictly necessary if you have EU visitors. [If it applies] Sources: ePrivacy Directive Art. 5 (https://legislation.gov.uk/eudr/2002/58/article/5)
- [ ] If users can create an account, let them delete it inside the app, and on Google Play also give a web link for deletion. [If it applies] Sources: Apple account deletion (https://developer.apple.com/support/offering-account-deletion-in-your-app/), Google Play account deletion (https://support.google.com/googleplay/android-developer/answer/13327111)
- [ ] Fill in Apple's App Privacy answers and Google Play's Data safety form, including your SDKs, and redo them when your data use changes. [If it applies] Sources: Apple App Privacy details (https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy), Google Play Data safety (https://support.google.com/googleplay/android-developer/answer/10787469)
- [ ] If you offer Google sign-in, put a homepage that describes the app on your own verified domain and get OAuth verification, because an unverified app is capped at 100 new users in total. [If it applies] Sources: Google OAuth verification (https://support.google.com/cloud/answer/13464321), Google unverified apps (https://support.google.com/cloud/answer/7454865)
- [ ] If you take payments with Stripe, show what you sell, the currency, contact details beyond a form, your refund and cancellation policy, your privacy policy and your business address. [If it applies] Sources: Stripe website checklist (https://docs.stripe.com/get-started/checklist/website)
- [ ] Update the policy and its effective date every time you add a vendor, SDK, analytics tool or AI provider. [Must do] Sources: Cal. Bus. & Prof. Code Sec. 22575 (https://california.public.law/codes/business_and_professions_code_section_22575)
- [ ] Check once a year whether you now pass the CCPA tests or another state's privacy law threshold. [Should do] Sources: CPPA thresholds (https://www.cppa.ca.gov/regulations/cpi_adjustment.html), IAPP state tracker (https://iapp.org/resources/article/us-state-privacy-legislation-tracker/)

## Stage 4: Consent before tracking

- [ ] Keep a one-page list of every tracker on your site and app: what it is for, what data it sends, whether it waits for consent, and whether you have a contract with the vendor. [Must do] Sources: CPPA on Tractor Supply (https://cppa.ca.gov/announcements/2025/20250930.html), CPPA on Honda (https://cppa.ca.gov/announcements/2025/20250312.html)
- [ ] For visitors in the EU, load no analytics, replay, ad pixel or chat widget that stores or reads data on their device until they accept. [If it applies] Sources: EDPB Guidelines 2/2023 (https://edpb.europa.eu/system/files/2024-10/edpb_guidelines_202302_technical_scope_art_53_eprivacydirective_v2_en_0.pdf), PostHog data collection (https://posthog.com/docs/privacy/data-collection)
- [ ] Put a Reject button on the same layer as Accept, with the same size and style. [If it applies] Sources: EDPB cookie banner report (https://www.edpb.europa.eu/system/files/2023-01/edpb_20230118_report_cookie_banner_taskforce_en.pdf), CNIL on Google, 2025 (https://www.cnil.fr/en/cookies-and-advertisements-inserted-between-emails-google-fined-325-million-euros-cnil)
- [ ] If you have a banner or an opt-out, test that Reject really stops tracking: click Reject, reload, and check the Network and Cookies tabs in your browser's developer tools. [If it applies] Sources: California AG on Healthline (https://oag.ca.gov/news/press-releases/attorney-general-bonta-announces-largest-ccpa-settlement-date-secures-155)
- [ ] Turn session replay off in your code, not only in the vendor dashboard, until you have a reason and a consent step. [Should do] Sources: PostHog config (https://posthog.com/docs/libraries/js/config), PostHog replay controls (https://posthog.com/docs/session-replay/how-to-control-which-sessions-you-record)
- [ ] If you record sessions, show notice and get consent before recording starts. [If it applies] Sources: DLA Piper on Javier (https://www.dlapiper.com/en/insights/publications/2022/06/javier-v-assurance-iq-llc-et-al)
- [ ] If you record sessions, mask all inputs and sensitive text, block payment, login, settings and chat pages, and scrub network request bodies. [If it applies] Sources: PostHog replay privacy (https://posthog.com/docs/session-replay/privacy), Clarity masking (https://learn.microsoft.com/en-us/clarity/setup-and-installation/clarity-masking)
- [ ] Turn off autocapture and send only the named events you chose. [Should do] Sources: PostHog data collection (https://posthog.com/docs/privacy/data-collection)
- [ ] If the CCPA covers you and you sell or share data, honor Global Privacy Control as an opt-out and apply it to the whole logged-in account. [If it applies] Sources: 11 CCR 7025 (https://www.law.cornell.edu/regulations/california/11-CCR-7025), California AG on Sephora (https://oag.ca.gov/news/press-releases/attorney-general-bonta-announces-settlement-sephora-part-ongoing-enforcement), California AG on Disney (https://oag.ca.gov/news/press-releases/california-wont-let-it-go-attorney-general-bonta-announces-275-million)
- [ ] Do not ask for ID just to opt out, and test your opt-out form after every deploy. [If it applies] Sources: CPPA on Todd Snyder (https://cppa.ca.gov/announcements/2025/20250506.html), CPPA on Honda (https://cppa.ca.gov/announcements/2025/20250312.html)
- [ ] If you use Microsoft Clarity and have visitors from the EEA, the UK or Switzerland, send the consent signal through its Consent API or a supported consent tool. [If it applies] Sources: Clarity consent mode (https://learn.microsoft.com/en-us/clarity/setup-and-installation/consent-mode)
- [ ] Do not treat SB 690 as permission for session replay or chat recording; get consent before any tool captures what users type. [Should do] Sources: Baker Donelson on SB 690 (https://www.bakerdonelson.com/sb-690-signed-into-law-what-it-means-for-cipa/web-tracking-litigation), WilmerHale on SB 690 (https://www.wilmerhale.com/en/insights/blogs/wilmerhale-privacy-and-cybersecurity-law/20261006-cipa-reform-signed-into-law)

## Stage 5: Sensitive data: health and kids

- [ ] Write down whether your app collects any health information, including symptoms, medications, fertility, mood or mental health, and keep the answer with your other launch notes. [Must do] Sources: FTC Health Breach Notification Rule (https://www.ftc.gov/news-events/news/press-releases/2024/04/ftc-finalizes-changes-health-breach-notification-rule), FTC on GoodRx (https://www.ftc.gov/news-events/news/press-releases/2023/02/ftc-enforcement-action-bar-goodrx-sharing-consumers-sensitive-health-info-advertising)
- [ ] Remove ad pixels and ad SDKs from every screen and page where users enter or read health information. [If it applies] Sources: FTC on GoodRx (https://www.ftc.gov/news-events/news/press-releases/2023/02/ftc-enforcement-action-bar-goodrx-sharing-consumers-sensitive-health-info-advertising), FTC on BetterHelp (https://www.ftc.gov/news-events/news/press-releases/2023/03/ftc-ban-betterhelp-revealing-consumers-data-including-sensitive-mental-health-information-facebook)
- [ ] Rename the events, page titles and URLs you send to analytics and ad tools so that none of them names a condition, a drug or a diagnosis. [If it applies] Sources: California AG on Healthline (https://oag.ca.gov/news/press-releases/attorney-general-bonta-announces-largest-ccpa-settlement-date-secures-155), FTC on GoodRx (https://www.ftc.gov/news-events/news/press-releases/2023/02/ftc-enforcement-action-bar-goodrx-sharing-consumers-sensitive-health-info-advertising)
- [ ] Never upload emails, phone numbers or ad IDs from a health app to an ad platform for targeting. [If it applies] Sources: FTC on GoodRx (https://www.ftc.gov/news-events/news/press-releases/2023/02/ftc-enforcement-action-bar-goodrx-sharing-consumers-sensitive-health-info-advertising), FTC on BetterHelp (https://www.ftc.gov/news-events/news/press-releases/2023/03/ftc-ban-betterhelp-revealing-consumers-data-including-sensitive-mental-health-information-facebook)
- [ ] Check that your privacy policy names every place health data goes, and that the app does exactly what the policy says. [If it applies] Sources: FTC Flo Health case (https://www.ftc.gov/legal-library/browse/cases-proceedings/192-3133-flo-health-inc), FTC on BetterHelp (https://www.ftc.gov/news-events/news/press-releases/2023/03/ftc-ban-betterhelp-revealing-consumers-data-including-sensitive-mental-health-information-facebook)
- [ ] Add health data to your breach plan, and treat data sent to a third party without permission as a breach that needs notices. [If it applies] Sources: FTC Health Breach Notification Rule (https://www.ftc.gov/news-events/news/press-releases/2024/04/ftc-finalizes-changes-health-breach-notification-rule), Federal Register, 2024 amendments (https://www.govinfo.gov/content/pkg/FR-2024-05-30/pdf/2024-10855.pdf)
- [ ] Do not let a third-party SDK or recording tool capture health entries or private messages, because California's recording law needs every party's consent. [If it applies] Sources: Meta 10-Q on the Flo verdict (https://www.sec.gov/Archives/edgar/data/0001326801/000162828026050705/meta-20260630.htm), Penal Code 637.2 (mirror) (https://codes.findlaw.com/ca/penal-code/pen-sect-637-2/)
- [ ] If you have users in Washington and handle anything that could reveal health, have a lawyer check your app against the My Health My Data Act. [If it applies] Sources: RCW 19.373.090 (https://app.leg.wa.gov/RCW/default.aspx?cite=19.373.090), Orrick on the first lawsuit (https://www.orrick.com/en/Insights/2025/02/First-Lawsuit-Filed-Under-Washingtons-My-Health-My-Data-Act)
- [ ] Write down who your app is for, and if it is for a general audience, do not market it to children under 13. [Must do] Sources: FTC COPPA compliance plan (https://www.ftc.gov/business-guidance/resources/childrens-online-privacy-protection-rule-six-step-compliance-plan-your-business), FTC COPPA FAQ (https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions)
- [ ] When you learn that a user is under 13, for example from a parent's email, get a parent's consent or delete that user's data, and log what you did. [Must do] Sources: FTC COPPA FAQ (https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions)
- [ ] If you ask for age, use a neutral age gate: empty birth date fields, no default, no "over 12" checkbox, and a cookie so the answer cannot be changed. [If it applies] Sources: FTC COPPA FAQ (https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions)
- [ ] If your app is directed to children, get verifiable parental consent before you collect personal information, and separate consent before you share it with third parties. [If it applies] Sources: FTC COPPA compliance plan (https://www.ftc.gov/business-guidance/resources/childrens-online-privacy-protection-rule-six-step-compliance-plan-your-business), Federal Register, 2025 COPPA Rule (https://www.govinfo.gov/content/pkg/FR-2025-04-22/html/2025-05904.htm)
- [ ] Get verifiable parental consent before analytics or ad SDKs collect persistent identifiers in any part aimed at children, and remove them if you list in the App Store Kids Category. [If it applies] Sources: eCFR 16 CFR 312.2 (https://www.ecfr.gov/api/versioner/v1/full/2026-10-01/title-16.xml?part=312&section=312.2), Apple guideline 1.3 (Kids Category) (https://developer.apple.com/app-store/review/guidelines/)
- [ ] If children use your app, write a security program and a retention policy, and delete children's data when you no longer need it. [If it applies] Sources: Federal Register, 2025 COPPA Rule (https://www.govinfo.gov/content/pkg/FR-2025-04-22/html/2025-05904.htm), FTC announcement (https://www.ftc.gov/news-events/news/press-releases/2025/01/ftc-finalizes-changes-childrens-privacy-rule-limiting-companies-ability-monetize-kids-data)
- [ ] Before you ship a mobile app to users in Texas or Utah, check the current state of their app-store age laws. [If it applies] Sources: InfoLawGroup on Texas (https://www.infolawgroup.com/insights/2026/7/7/supreme-court-clears-the-way-texass-app-store-accountability-act-is-now-enforceable), Loeb and Loeb on Utah (https://www.loeb.com/en/insights/passle/2026/05/update-on-utah-app-store-law--another-waiting-game)

## Stage 6: Accessibility

- [ ] Pick WCAG 2.2 level AA as your target and write it in your project notes so your agent builds to it. [Must do] Sources: WCAG 2.2 (https://www.w3.org/TR/WCAG22/), WCAG 2.1 (https://www.w3.org/TR/WCAG21/)
- [ ] Give every meaningful image and icon button a text alternative, and mark decorative images so screen readers skip them. [Must do] Sources: WCAG 2.2 quick reference (https://www.w3.org/WAI/WCAG22/quickref/)
- [ ] Give every form field a visible label that stays when the user types, not only a placeholder. [Must do] Sources: WCAG 2.2 quick reference (https://www.w3.org/WAI/WCAG22/quickref/)
- [ ] Make every task work with a keyboard alone, with a visible focus outline that sticky headers and popups do not cover. [Must do] Sources: WCAG 2.2 (https://www.w3.org/TR/WCAG22/), WCAG 2.2 quick reference (https://www.w3.org/WAI/WCAG22/quickref/)
- [ ] Check text contrast and fix anything below 4.5:1 for normal text or 3:1 for large text. [Must do] Sources: WCAG 2.2 quick reference (https://www.w3.org/WAI/WCAG22/quickref/)
- [ ] Check your app against the six rules WCAG 2.2 added: focus not obscured, dragging, target size, consistent help, redundant entry and accessible login. [Should do] Sources: WCAG 2.2 (https://www.w3.org/TR/WCAG22/)
- [ ] Run axe, WAVE or Lighthouse on every key page and fix what they report. [Must do] Sources: axe DevTools (https://www.deque.com/axe/devtools/), WAVE (https://wave.webaim.org/), Lighthouse (https://developer.chrome.com/docs/lighthouse/overview)
- [ ] Do a keyboard-only pass and a screen reader pass through sign-up, login and your main task, because automated tools miss many problems. [Must do] Sources: WCAG 2.2 quick reference (https://www.w3.org/WAI/WCAG22/quickref/), WAVE (https://wave.webaim.org/)
- [ ] Publish an accessibility statement with your target standard, known gaps and a way to report problems. [Should do] Sources: Seyfarth Shaw on 2025 filings (https://www.adatitleiii.com/2026/03/federal-court-website-accessibility-lawsuit-filings-bounce-back-in-2025/)
- [ ] If you sell a covered consumer service to EU buyers, check whether you are above the microenterprise limits, and if so meet the European Accessibility Act. [If it applies] Sources: Directive 2019/882 Article 4 (https://www.legislation.gov.uk/eudr/2019/882/article/4), Article 3 definitions (https://www.legislation.gov.uk/eudr/2019/882/article/3), European Commission (https://commission.europa.eu/strategy-and-policy/policies/justice-and-fundamental-rights/disability/union-equality-strategy-rights-persons-disabilities-2021-2030/european-accessibility-act_en)
- [ ] If you sell to schools, cities or other public bodies in the US, be ready to show WCAG 2.1 AA conformance before their 2027 and 2028 deadlines. [If it applies] Sources: ADA.gov web rule first steps (https://www.ada.gov/resources/web-rule-first-steps/)
- [ ] Add an automated accessibility check to your tests so new pages do not slip back. [Should do] Sources: axe DevTools (https://www.deque.com/axe/devtools/), Lighthouse (https://developer.chrome.com/docs/lighthouse/overview)

## Stage 7: AI features

- [ ] Write down which kinds of AI feature your app has: chat, companion, generator, decision tool, or data sent to an AI company.
